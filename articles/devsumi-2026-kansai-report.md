## はじめに

2026年8月21日に梅田サウスホールで開催された [Developers Summit 2026 KANSAI](https://event.shoeisha.jp/devsumi/20260821)（デブサミ関西）に参加してきました。今年のテーマは「Re:Developer〜エンジニアの再定義〜」。AIエージェントが当たり前になりつつある今、エンジニアとして何をどう変えていくべきかを考えさせられる一日でした。

## 参加したセッション

当日聴いたのは次の4セッションです。

- **B-1 基調講演「2026年はAIエージェント『構築』元年となるか？」** 御田 稔（みのるん）さん［KDDIアジャイル開発センター］
- **A-5「AIで変わるエンジニアの働き方、求められる役割」** 直井 和久さん・西林 拓志さん［TRAILBLAZER］
- **A-6「生成AI時代のクレデンシャルとパーミッション設計 — AIに権限と鍵をどう渡し、あるいは渡さないのか」** 佐々木 拓郎さん［NRIネットコム］
- **A-7「10周回って、エージェント開発はRAGがすべてだった。〜開発現場で見えた実践知〜」** 為藤 アキラさん［BLUEISH］

## AIエージェントに任せる業務の広がり

複数のセッションに共通していたのが、AIエージェントに任せる範囲はもうコーディングだけではない、という話です。出張経費の計上や出退勤の打刻といった日常の雑務も、Claude Code や Codex などのエージェントで自動化していくべきだ、という主張が印象に残りました。

私自身、業務ではプロジェクトの月次レポート作成をAIに任せています。みのるんさんの講演では、出張のための新幹線のチケットの手配や経費精算などの雑務にも Claude Code を活用しているとのことでした。雑務にかける時間を限りなくゼロに近づけて、業務の中で本当に大事な「考えること」に時間を割けるようにしていきたいです。

## クレデンシャルの扱い

一方で、エージェントに任せる範囲を広げるほど重要になるのが権限と鍵の渡し方です。佐々木さんのセッションでは、AIエージェントにクレデンシャルを見せるべきではない、という原則が具体的に示されました。

- `.env` や `~/.aws` 以下は、AIエージェントからリードもできないように設定する
- AWSコマンドの実行などは、基本的にエージェントに実行させず、人間が自分で実行する方が安全
- PC全体をAIが読める状態にせず、サンドボックスやコンテナを活用して読める範囲を区切る

耳が痛い話でした。正直、私はクレデンシャルが見える状態のまま作業してしまっていました。良くないなと思いつつ放置していた部分なので、これはすぐに取り入れます。

## AIエージェントの作り方

自分でAIエージェントを作る、というテーマでも収穫がありました。

以前 Dify や LangChain でエージェント作成を試したことがあるのですが、正直うまくいかず、難しいなという印象のまま止まっていました。みのるんさんの基調講演で紹介されていた Amazon Bedrock AgentCore は、コーディング量が少なく、そのままサーバーレスでデプロイできて、個人で使ってもコストがかかりにくい構成とのこと。今のところ使わない理由が見当たらないので、再挑戦はここから始めようと思います。

為藤さんのセッションで語られていたのは、AIエージェントの品質の差別化は最終的にほとんどRAGの部分で決まる、という実践知でした。ポイントは2つです。

- 用途や情報の質に適したRAGの種類を選択すること
- どの情報をRAGに入れ、どの情報をプロンプトに入れ、どの情報を CLAUDE.md のような指示書に入れるか——この使い分けがエージェントの品質を左右すること

これはなるほどなと思いました。以前フジロックについて回答してくれるAIエージェントを作ろうとしたとき、一番困ったのがまさにRAGの部分だったんです。どのモデルを使い、どう設定し、チャンクをどう分割するかが全く分かりませんでした。

その点で期待しているのが、みのるんさんの講演で紹介されていた Amazon S3 Vectors です。Bedrock ナレッジベースと組み合わせると、チャンク分割や埋め込み生成のあたりをマネージドでやってくれるらしいです。チャンク分割でつまずいた身としては、まずはここから試してみるのが良さそうです。

## AI時代のエンジニアのあり方 — 3つの軸

テーマである「エンジニアの再定義」については、登壇者それぞれが悩みながら模索している印象でした。そんな中でも共通していたのは、「エンジニアがもうコードを手書きする時代ではない」という前提と、そのうえでAIの成果物に責任を持てるかどうかが重要になる、という点です。

では責任を持てるエンジニアとしてどこを伸ばすのか。この問いに全体像を示してくれたのが TRAILBLAZER のお二人のセッションで、話を聞きながら、キャリアの広げ方は3つの軸で整理できると感じました。

- **X軸（技術領域の拡張）**: エンジニア領域の中で扱う技術を横に広げる方向。お二人は、もともと Kotlin やスマホアプリを一番の強みとしながら、Webフロントエンドやサーバーサイドへと領域を広げていこうとしているそうです。「Kotlin と Swift でもまた勝手が違う」という話もあり、そうした勘所を見極めながら広げていくのがこの軸です。
- **Y軸（役割の拡張）**: エンジニアの枠を超えて役割を広げる方向。例えば、エンジニアをやりながらプロダクト領域に関わり、ユーザーの要望を聞いて要件を固めるところまで守備範囲を広げていくイメージです。作る側からプロダクトを考える側へ、担う範囲そのものを広げていく方向性です。
- **Z軸（専門性の深化）**: セキュリティや品質、パフォーマンス、アーキテクチャといった方向により知識をつけて、自分の強みとしていく方向。AIを活用しながら専門領域を深掘りしていくスペシャリスト路線です。

## おわりに

参加して持ち帰ったアクションは3つです。

- AgentCore + S3 Vectors でAIエージェント作成に再挑戦する
- クレデンシャル管理をすぐに改善する（`.env` や `~/.aws` をエージェントから読めなくする）
- 日常の雑務にもAIエージェントをもっと活用していく

また、キャリアの広げ方をX軸・Y軸・Z軸というかたちで自分なりに整理できたのも良かったです。
